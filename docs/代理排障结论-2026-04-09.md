# 代理排障结论

## 背景
claude-mobile 在 Railway 上调用 Claude 时出现失败。经过本次排查，已经确认主要问题不在前端页面、不在数据库，也不在 Express 路由本身，而在上游代理链路。

## 本次已确认的结论

### 1. 报错落点不在 chat 路由逻辑本身
聊天主流程里的失败点表面上出现在 [backend/routes/chat.js:203](../backend/routes/chat.js#L203)：

```js
const assistantContent = await sendMessage(promptMessages, { model });
```

但这只是调用栈位置。真正失败的是 `sendMessage(...)` 发往上游 Claude 的请求，也就是 [backend/services/claude.js](../backend/services/claude.js)。

### 2. 当前使用的是代理，不是官方 Anthropic
Railway 日志里已经出现过这些典型标记：

- `x-oneapi-request-id`
- `under group ... (distributor)`
- `x-new-api-version`

这说明当前请求经过的是 OneAPI / 分销代理，而不是官方 Anthropic 接口。

### 3. 代理组 `Claude C站反重力` 是动态共享通道
已经确认这个组存在下面这些情况：

- 并发波动
- 限流
- 时段性通道不足
- 一个通道可能承接多个模型
- 哪个模型当前能接就接哪个

这意味着：

- 同一个代理 key，不同时间请求结果可能不同
- 同一个模型名，显示可用不代表下一次请求就一定可用
- 电脑端能稳定，不代表移动版同一时刻也能稳定

### 4. 代理失败有两类典型表现
#### A. 通道/模型不可用
日志里已经出现过：

- `model_not_found`
- `No available channel for model ...`
- HTTP `503`

这说明请求到达了代理，但代理当前没有合适的模型通道可以接。

#### B. 代理响应结构不完整
日志里还出现过 thinking-only 的情况，也就是：

- 上游只返回 `thinking`
- 没有返回可展示的 `text`

这说明即使代理接住了请求，也不代表它对 Anthropic Messages API 的兼容是完整稳定的。

### 5. 前端传入的 `model` 之前会覆盖后端默认模型
此前日志里曾同时出现多个模型名：

- `claude-3-5-sonnet-20240620`
- `claude-3-5-haiku-20241022`
- `claude-opus-4-6`

这说明前端请求体中的 `model` 覆盖了后端环境变量中的默认模型。

### 6. 已完成的后端修正
后端已经改成：

- 不再信任前端传入的 `model`
- 统一只使用环境变量里的模型
- 保留更清晰的上游日志输出，便于继续判断问题落在模型、通道还是响应格式

## 当前最准确的判断
现在的问题本质上不是“移动版不能用代理 key”，而是：

**这个代理组是动态共享通道，模型可用性和接口兼容性都不是稳定常量。**

因此会同时出现这些现象：

- 某次使用记录显示模型是 `claude-opus-4-6`
- 某次请求却报 `model_not_found`
- 某次请求又出现 only-thinking 无正文

这些现象彼此并不矛盾，反而符合这个代理组的运行方式。

## 推荐的下一步实现方向

### 方案一：继续走代理，但后端做动态兜底
推荐优先考虑这个方向。

建议后端实现：

1. 使用候选模型列表，例如：
   - `ANTHROPIC_MODEL_CANDIDATES=claude-opus-4-6,claude-3-5-sonnet-20240620,claude-3-5-haiku-20241022`
2. 请求时按优先级尝试模型
3. 遇到以下错误自动切下一个候选模型：
   - `503`
   - `No available channel`
   - `model_not_found`
4. 全部失败后，统一返回更明确的提示：
   - `当前代理通道繁忙，请稍后重试`
   - `当前模型通道暂时不可用，请稍后再试`

### 方案二：如果代理提供真实模型列表 API
如果代理后台不只是网页展示，而是提供可调用的模型列表接口，那么可以进一步做成：

- 后端动态获取当前组可见模型
- 与本地配置的候选模型取交集
- 只在交集里做 fallback

### 方案三：如果只是要先跑通
最直接的方案仍然是：

- 删除 `ANTHROPIC_BASE_URL`
- 改用官方 Anthropic 接口
- 使用官方 key

这能绕开代理动态通道带来的不稳定性。

## 以后继续排障时重点看什么
继续看 Railway 日志时，优先关注这些信号：

- `Claude upstream response`
- `Claude API 调用失败`
- `x-oneapi-request-id`
- `under group ... (distributor)`
- `model_not_found`
- `No available channel`
- 是否只有 `thinking` 没有 `text`

## 一句话总结
当前问题最合理的归因是：

**代理组 `Claude C站反重力` 的动态共享通道机制，叠加 Anthropic 接口兼容性不稳定，导致同一个 key 在不同请求时刻表现不一致。**

所以后续不应再把它当成单一固定模型接口，而应该按“动态模型可用性 + 后端 fallback”来设计。
